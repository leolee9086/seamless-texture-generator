# 性能瓶颈分析报告

## 问题现象

用户调整任意简单参数（如亮度），画面都会"转圈圈"等待较长时间才能看到结果。

---

## 根本原因

### 1. 无增量处理：每次调整都从头开始

当前处理管线 (`processImageToTileable`) 每次都执行完整流程：

```
  ┌─────────────────────────────────────────────────────────────┐
  │              每次参数变化触发的完整流程                        │
  ├─────────────────────────────────────────────────────────────┤
  │                                                              │
  │  1. loadAndScaleImage()     ← 重新加载并缩放原图 ⚠️           │
  │     ├── new Image()                                          │
  │     ├── img.src = dataURL   ← 解码 Base64                   │
  │     ├── scaleImageToMaxResolution()                          │
  │     └── imageDataToGPUBuffer()                               │
  │                                                              │
  │  2. executeLUTProcess()     ← 即使没有 LUT 也会执行检查       │
  │                                                              │
  │  3. executeHSLAdjust()      ← HSL 调整                       │
  │                                                              │
  │  4. 遍历所有中间件          ← 曝光、去雾、清晰度、亮度等       │
  │     for (middleware of allMiddlewares)                       │
  │                                                              │
  │  5. executeTileableProcess() ← 无缝化处理                    │
  │     ├── gpuBufferToImageData()                               │
  │     ├── makeTileable()     ← CPU 密集型                      │
  │     └── imageDataToGPUBuffer()                               │
  │                                                              │
  │  6. convertToDataURL()      ← GPU→Canvas→Base64 ⚠️           │
  │                                                              │
  └─────────────────────────────────────────────────────────────┘
```

**问题**：用户只是调整了亮度，却要重新执行整个管线！

---

### 2. 重复解码 DataURL

`loadAndScaleImage()` 每次都从 DataURL (Base64 字符串) 加载图片：

```typescript
// imageLoad.utils.ts
const img = new Image();
img.src = originalImage;  // ← originalImage 是个几MB的 Base64 字符串
```

**问题**：Base64 解码 + Image 解码是昂贵操作，每次调整都重新执行。

---

### 3. 无缝化处理每次都执行

`tileable.utils.ts` 中的无缝化逻辑：

```typescript
// 即使 borderSize == 0，前后的 buffer 转换仍然可能有开销
const imageData = await gpuBufferToImageData(data.buffer, ...)
const processedImageData = await makeTileable(imageData, borderSize, null)
```

`makeTileable()` 是一个 CPU 密集型操作，涉及边缘混合算法。

---

### 4. 输出再次转换

`convertToDataURL()` 将 GPU 结果转换回 Base64：

```
GPUBuffer → Canvas → toDataURL() → Base64 字符串
```

这个过程也有性能开销，尤其是高分辨率图片。

---

### 5. Watch 触发多余处理

`useTextureGenerator.watch.ts` 中，多个参数共享同一个 watch：

```typescript
watch([
    state.borderSize,
    adjustmentParams.exposureStrength,
    adjustmentParams.exposureManual,
    adjustmentParams.dehazeParams,
    adjustmentParams.clarityParams,
    adjustmentParams.luminanceParams,
    // ... 等等
], () => {
    debouncedProcessImage()  // 任何参数变化都触发完整处理
}, { deep: true })
```

虽然有 300ms 的 debounce，但最终还是会触发完整流程。

---

## 性能热点总结

| 阶段 | 耗时原因 | 是否可避免 |
|------|----------|------------|
| 图像加载 | 每次从 DataURL 解码 | ✅ 可缓存 |
| GPU Buffer 创建 | 每次重新上传到 GPU | ✅ 可复用 |
| 中间件遍历 | 即使无效也会检查 | ⚠️ 开销小 |
| 无缝化处理 | CPU 密集型边缘混合 | ✅ 参数无关可跳过 |
| DataURL 输出 | GPU→CPU→Base64 | ✅ 可用 ImageBitmap |

---

## 优化建议

### 方案一：分层缓存 (推荐)

将处理管线分成多个阶段，每个阶段缓存结果：

```
┌────────────────┐
│ 原图 DataURL   │ ← 输入（不变）
└───────┬────────┘
        ▼
┌────────────────┐
│ 缩放后 ImageData│ ← 缓存层1：图片加载后缓存
└───────┬────────┘
        ▼
┌────────────────┐
│ GPU Buffer     │ ← 缓存层2：上传GPU后缓存
└───────┬────────┘
        ▼
┌────────────────┐
│ 效果处理结果    │ ← 缓存层3：只有相关参数变化时才重算
└───────┬────────┘
        ▼
┌────────────────┐
│ 无缝化结果      │ ← 缓存层4：只有 borderSize 变化时才重算
└───────┬────────┘
        ▼
┌────────────────┐
│ 输出 ImageBitmap│ ← 直接用 ImageBitmap，避免 DataURL
└────────────────┘
```

**实现要点**：
- 每个缓存层记录"依赖参数 hash"
- 只有依赖参数变化时才重算该层及之后的层
- 用 `WeakMap` 或 `Map` 存储缓存

---

### 方案二：参数分组 + 局部更新

将参数按处理阶段分组：

```typescript
// 参数分组
const 基础参数 = ['maxResolution']     // 变化时：重算全部
const 色彩参数 = ['hsl', 'lut', 'exposure']  // 变化时：从色彩阶段开始
const 效果参数 = ['dehaze', 'clarity']  // 变化时：从效果阶段开始
const 无缝参数 = ['borderSize']        // 变化时：只重算无缝化

// 分组 watch
watch(色彩参数, () => 从色彩阶段开始处理())
watch(效果参数, () => 从效果阶段开始处理())
watch(无缝参数, () => 只执行无缝化())
```

---

### 方案三：用 ImageBitmap 替代 DataURL

避免 Base64 编解码开销：

```typescript
// 当前：DataURL (Base64 字符串)
state.processedImage.value = await convertToDataURL(pipelineData)

// 优化后：ImageBitmap (原生对象)
state.processedImage.value = await createImageBitmap(canvas)
// Viewer 组件直接 drawImage(imageBitmap)
```

**注意**：需要修改 Viewer 组件以支持 `ImageBitmap` 类型输入。

---

### 方案四：Web Worker 离线处理

将 CPU 密集操作移到 Worker：

```typescript
// 主线程
worker.postMessage({ type: 'makeTileable', imageData, borderSize })

// Worker
onmessage = async (e) => {
    const result = await makeTileable(e.data.imageData, e.data.borderSize, null)
    postMessage({ type: 'result', imageData: result })
}
```

**好处**：UI 不会卡顿，即使处理时间长也不会"转圈圈"感觉卡死。

---

## 快速修复建议 (低成本)

如果暂时没有时间做大重构，可以先做这些小优化：

1. **缓存加载后的 ImageData**
   - 在 `loadAndScaleImage` 后缓存结果
   - 只有原图变化时才重新加载

2. **跳过无关的无缝化处理**
   - 如果 `borderSize == 0` 且上次也是 0，直接返回

3. **使用 OffscreenCanvas**
   - 在 Worker 中处理图像，减少主线程阻塞

## CPU-GPU 传输边界分析

### 当前传输模式

每个处理节点都执行 **GPU→CPU→处理→CPU→GPU** 的完整往返：

```
┌─────────────────┐
│   imageLoad     │ CPU→GPU (ImageData → GPUBuffer)
└────────┬────────┘
         ▼
┌─────────────────┐
│   LUT 处理      │ GPU→CPU→处理→CPU→GPU
└────────┬────────┘
         ▼
┌─────────────────┐
│   HSL 调整      │ (WebGPU Shader，无往返) ✅
└────────┬────────┘
         ▼
┌─────────────────┐
│  曝光调整       │ GPU→CPU→处理→CPU→GPU ⚠️
│  (exposureNode) │
└────────┬────────┘
         ▼
┌─────────────────┐
│  去雾调整       │ GPU→CPU→处理→CPU→GPU ⚠️
│  (dehazeNode)   │
└────────┬────────┘
         ▼
┌─────────────────┐
│  清晰度调整     │ GPU→CPU→处理→CPU→GPU ⚠️
│  (clarityNode)  │
└────────┬────────┘
         ▼
┌─────────────────┐
│  亮度调整       │ GPU→CPU→处理→CPU→GPU ⚠️
│  (luminanceNode)│
└────────┬────────┘
         ▼
┌─────────────────┐
│  无缝化处理     │ GPU→CPU→处理→CPU→GPU ⚠️
│  (tileable)     │
└────────┬────────┘
         ▼
┌─────────────────┐
│  输出转换       │ GPU→CPU→Canvas→Blob URL
└─────────────────┘
```

### 传输热点统计

| 节点 | gpuBufferToImageData | imageDataToGPUBuffer | 备注 |
|------|:---:|:---:|------|
| imageLoad | - | 1次 | 输入 |
| LUT | 1次 | 1次 | CPU LUT 查表 |
| HSL | - | - | ✅ 纯 GPU Shader |
| 曝光 | 1次 | 1次 | CPU 处理 |
| 去雾 | 1次 | 1次 | CPU 处理 |
| 清晰度 | 1次 | 1次 | CPU 处理 |
| 亮度 | 1次 | 1次 | CPU 处理 |
| 无缝化 | 1次 | 1次 | CPU 处理 |
| 输出 | 1次 | - | 输出 |

**单次完整处理的传输次数**: 
- `gpuBufferToImageData`: 7次
- `imageDataToGPUBuffer`: 6次
- **总传输次数**: 13次 GPU↔CPU 数据拷贝

### 传输成本估算

假设 2048×2048 RGBA 图像:
- 单张图像大小: 2048 × 2048 × 4 = **16 MB**
- 单次 GPU→CPU 传输: ~5-10ms (取决于 GPU)
- 单次 CPU→GPU 传输: ~3-5ms

**总传输时间**: 13 × 5ms ≈ **65ms** (仅传输，不含处理)

### 问题代码示例

每个节点都有类似的模式：

```typescript
// dehazeNode.ts (第19-33行)
// GPU→CPU
const imageData = await gpuBufferToImageData(pipelineData.buffer, ...)

// CPU 处理
const processedImageData = await applyDehazeAdjustment(imageData, ...)

// CPU→GPU
const processedBuffer = device.createBuffer({ ... })
new Uint8Array(processedBuffer.getMappedRange()).set(processedImageData.data)
processedBuffer.unmap()
```

### 优化方向

#### 方案 A: 合并传输（短期）

将多个 CPU 处理合并，减少传输次数：

```
当前: GPU→CPU→曝光→CPU→GPU→CPU→去雾→CPU→GPU→CPU→清晰度→CPU→GPU
优化: GPU→CPU→(曝光→去雾→清晰度)→CPU→GPU
```

传输次数从 6次 减少到 2次。

#### 方案 B: GPU Shader 化（中长期）

将 CPU 处理逻辑迁移到 WebGPU Compute Shader：

```
当前: GPU→CPU→曝光处理→CPU→GPU
优化: GPU→曝光Shader→GPU (无传输)
```

**适合 GPU 化的节点**:
- ✅ 曝光调整 - 简单的像素级运算
- ✅ 亮度/对比度 - 简单查表或运算
- ⚠️ 清晰度 - 需要卷积，中等复杂度
- ⚠️ 去雾 - 暗通道先验算法较复杂

#### 方案 C: 延迟传输（实验性）

只在需要时才执行 GPU→CPU 传输：
- 全 GPU 处理链保持 GPUBuffer/GPUTexture
- 只在需要 CPU 处理时才读回
- 输出时使用 `canvas.drawImage()` + WebGPU Canvas 互操作

### 已有的良好实践

- **HSL 调整** (`executeHSLAdjust`) 使用 WebGPU Shader，无传输开销 ✅
- **guard 函数** 检查参数是否需要处理，避免无效传输 ✅
